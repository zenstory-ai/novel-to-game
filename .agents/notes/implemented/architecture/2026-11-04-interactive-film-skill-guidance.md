# Agent Note: 互动影游的交互语法与生成媒体闸门写进 skills

Status: implemented

## Problem

金瓶梅示例升级为互动影游时，限时沉默、察言观色、按住动作、「她记下了」与剧情树这些交互，以及「先打磨再生成影像」
「选择之后用剧情过场演出后果」「生成音频的后期与回落」这些生产经验，只存在于一个示例里。下一部小说改成互动影游时，
各 skill 没有地方告诉 agent 这些取舍。

## Decision

- `game-world-design` 新增 `references/interactive-film-method.md`，SKILL.md 在选择之后要用剧情动画演出后果时指向它：
  什么才算影游（过场演后果，静帧微动不算）、按选择点 × 选项配过场、过场的写法与字幕、五种交互语法放在哪里与不放在哪里、
  沉默分支与热区的写法、公平与可访问性、交付检查。
- `game-concept` 的概念方法说明互动影游通常是 `narrative-led`，先用文字与静帧验证交互后果，再按「配过场的选择点 × 选项数 + 结局」估算影像预算。
- `game-art-direction` 的方法补过场的方向：立绘与背景作参考锁身份、第一人称多镜头、一段一个转折、末帧落点、字幕条、
  声音与回落；静帧循环微动只算待机氛围层；
  曲目与音效同样登记用途与替代表达。
- `game-build` 的 `generative-media-pipeline.md` 保留成本闸门、生成音乐与音效的后期、运行时回落和供应商边界（调用方式与密钥留在项目外）。
  过场的做法单独放进 `references/cutscene-production.md`，SKILL.md 在要播剧情过场时指向它。内容包括：台账与提示词；
  画面出错时回到提示词找原因；抽帧审片与重做；按对白校准字幕；运行时行为；体积与托管额度。
  这些都写成通用原因，金瓶梅里遇到的具体情况只当例子，不另写清单。
- 读字背景乐以长音为主，密集拨弦会打断阅读；风格容易混淆时写明要排除什么，多生成几版挑最柔和的一版。
  `game-art-direction` 写方向，`game-build` 写怎么挑。`game-world-design` 补一条：过场台词先定稿再生成，开口的台词要短。
- `game-qa` 的测试设计方法补互动影游的检查：穷举沉默/细节/动作分支、倒计时暂停、热区对位、选择后播出对应过场、字幕换句与暂停、
  末帧回落、首次手势前不出声、
  后台页节流的处理。

## Alternatives considered

- **把影像写成「让已批准的静帧循环微动」**（本分支最初写进 skills 的做法）— 最强理由：首尾帧同图，接缝与热区都不出错，成本最低。
  否决原因：负责人指出这是「动态的人物绘画」，不是互动影游；影游的影像要在选择之后演出有剧情的后果。
  skills 里把它降为可选的待机氛围层，并明确它不能代替过场。

- **单独新建一个 interactive-film skill** — 最强理由：一处读全。否决原因：它会同时拥有概念、设计、美术、构建与 QA 的决定，
  违反规划 owner 分离（见 [planning-owner-separation](2026-07-18-planning-owner-separation.md)）；按 owner 分别放进各自的 references 更符合现有结构。
- **只在示例里留下实现** — 最强理由：零维护成本。否决原因：示例代码不会被其他项目的 agent 读到，取舍理由会丢。

## Consequences

- 收益：下一部互动影游从概念阶段就知道影像预算怎么分、哪些选择不能限时、生成媒体什么时候做。
- 代价：五个 skill 各多一段内容，需要随示例的实际做法同步。skills 总行数接近 1300 行的上限，新增内容靠合并重复段落腾出空间。
