# Agent Note: 2.5D 角色序列帧走“目标图 → 三维模型 → 按游戏镜头烘焙”的按需路线

Status: implemented

## Problem

2.5D 角色要在多个方向、多个动作之间保持同一张脸、同一套服装和同一比例。逐帧二维生成做不到稳定一致，
转向和动作切换时身份会漂；《西游记》示例的 `assets/units/` 共 25 张图，每个角色或变身形态各一张静态立绘，
没有多方向序列。`game-build`
目前只有 Blender 一条三维资产路线，它针对可编辑几何与场景装配，没有覆盖“从批准的角色目标图得到多方向
序列帧”这一需求。

## Decision

新增按需读取的 `game-build/references/baked-sprite-workflow.md`（20 行），`game-build/SKILL.md` 在 2.5D 角色或
物件需要多方向、多动作且身份一致的序列帧时读取。路线为：以批准的角色目标图生成三维模型并核对识别锚点 →
自动绑定并套用 GAME_DESIGN 用到的动作 → 在目标引擎无头模式或三维软件中按游戏镜头、投影、主光和描边规则
逐方向逐动作渲染，统一方向数、帧率、画布和脚底锚点 → 打包图集、配置资产键，在实际游戏镜头里检查转向顿挫、
脚步打滑、锚点抖动和光色。工具与服务不指定，按当前能力、许可与费用选择。

## Alternatives considered

- **先做端到端构建评估再合并** — 最强理由：
  [构建打磨轮与资产参考否决记录](../../rejected/feature/2026-10-03-build-polish-round-and-asset-workflow.md)里，
  一份二维资产生产参考扩到每组 4 次构建后收益消失，构建阶段的资产规则不能凭读感上线。否决原因：维护者
  2026-10-19 决定跳过评估直接落地；本条只在选择 2.5D 多方向角色时读取，不影响其他项目。
- **并入 `blender-asset-workflow.md`** — 最强理由：少一个文件。否决原因：两条路线的输入、工具与验收都不同，
  Blender 只是可选的渲染环境之一；合并会让“不因项目是 3D 就默认采用 Blender”的边界变模糊。
- **继续用二维生成补差分** — 最强理由：工具链最短。否决原因：单张图出差分能处理表情与少量姿态，覆盖不了
  八方向乘多动作的组合。

## Consequences

- 收益：选择 2.5D 的项目有一条能保持身份一致的序列帧路线，转向与动作切换的检查项写明。
- 代价：依赖图生三维、自动绑定和无头渲染三类外部能力，任一缺失时这条路线不可用，需退回已有表现并记录限制。
- 风险：与被否决的二维资产参考同类，未证明能提高构建评分；按需读取把影响范围限定在 2.5D 多方向角色。

## Verification

`python3 scripts/validate_repo.py` 与 `python3 -m unittest discover -s tests -v` 通过，单个 reference 20 行，
低于 150 行预算。按维护者决定未做端到端评估，也未在任何示例中实际运行这条路线。
