# 测试设计方法

[qa-contract.md](qa-contract.md) 规定**验什么**和**判据**。本文讲**怎么设计这些检查**，
以及验证工作本身会怎么烂掉。

一句话原则：**检查的价值等于它失败时你能学到什么。** 一个永远通过的断言不是保障，
是噪声。

## 一、三类检查，不要混

| 类 | 断言什么 | 判据 | 例 |
|---|---|---|---|
| **确定性** | 规则、数值、状态迁移 | 布尔，同输入必同输出 | 相克系数 ×1.5、门槛 ≥30、存档往返一致 |
| **观察性** | 画面上出现了什么 | 人或干净上下文子代理裁决，附证据帧 | 招牌帧要素齐、前提四问（我是什么 / 我要什么 / 什么终结这一局 / 这是哪一类游戏）能否只凭画面答出 |
| **不可判定** | 好不好玩、平衡、留存 | **不判**，交人工试玩协议 | 「这一局有意思吗」 |

把第三类写成第一类是最常见的造假方式：测试文件里出现某句策划文案，只能证明文字没变，
不能证明规则正确或游戏可玩。

反过来也有一种逃逸：把**观察性**的问题推给「不可判定」。「这是哪一类游戏」看起来像口味题，
其实不是——它问的是画面有没有传达出品类，判据是裁决者的逐字回答与 `CONCEPT.md` 已声明的
先例名单是否字面命中，二元可判。真正不可判定的是「好不好玩」，不是「看不看得懂」。

## 二、确定性检查：从门槛反推用例

每一个数值门槛、每一个结局条件、每一个破裂/冷却条件，都按下面三点各取一次：

- **门槛下方一格**：不该触发。
- **门槛上**：该触发。
- **门槛上方**：仍该触发，且不产生第二次副作用（一次性门控最容易在这里破）。

状态迁移同理：列出所有相位（白天／夜里／战斗／结算／重开），逐条确认**每个出边**都被走过
至少一次，包括「拒绝」和「退出」这类没人爱测的边。

**期望值必须来自设计文档，不是来自实现。** 用实现自己的常量去验收实现，过滤逻辑跑通、
用同一份规则验收就必然通过，无论漏掉多少。写检查时手边只放设计文档。

## 三、断言要盯住「设计承诺」，而不是「代码路径」

区别很大：

- 盯代码路径：「`applyBuff` 被调用了」——重构就红，改设计不红。
- 盯设计承诺：「用了这件道具后，敌方攻击确实上升，且只对设计声明的那类敌人生效」
  ——重构不红，设计被违反就红。

后者才有价值。做法是把断言写在**引擎的输入/输出**上，不写在内部函数上。

## 四、覆盖会静默腐烂——这是最容易被漏掉的一条

真实经历，值得当成通则记住：

> 某个演示核心卖点的脚本分支挂在「第 N 个被叫到的单位」上。后来敌方 AI 被调强，
> 战斗回合数变短，那个单位再也没被叫到，分支不再执行，证据帧消失。
> **测试计数一个没少，没有任何东西变红。**

通则：**每一个「演示设计承诺」的脚本分支，都必须挂一条断言。** 没有断言的演示分支，
在下一次平衡调整后会静默失效，而你会以为它还在跑。

自查：把脚本里所有「截一帧 / 走一段演示」的地方列出来，逐个问「如果它没执行，
哪条断言会红」。答不出来的，补断言，或者删掉这段演示别自欺。

推论：**改平衡之后要重跑覆盖，并比对产出的证据清单**，不是只看通过数。数量相同而
内容变了，是最难发现的回退。

## 五、修一个缺陷，配一条回归

每条修掉的 `blocker` / `major` 都要留一条**能复现原缺陷**的断言。写法：先让它在修复前
失败（哪怕只在本地临时改回去验一次），再让它在修复后通过。没有失败过的回归测试，
不能保证它盯的是那个缺陷。

回归测试写在实现方的套件里（它是实现缺陷），独立验证留在 QA 侧（它验的是设计承诺）。
两者分开跑，不要合并。

## 六、循环外的结算点是缺陷高发区

任何**在正常行动循环之外**改变生死的东西，都要单独检查它之后有没有跑胜负/结束判定：

- 剧情脚本造成的伤害或治疗
- 一次性门控的支援、增援、天灾
- 持续伤害/回血的回合末结算
- 阶段转换（换形态、换阶段、换幕）
- 道具或环境的即时效果

漏一个的后果不是数值不对，而是**状态机带着不该继续的局面继续跑**，然后在某个取目标、
取当前单位的地方拿到空值崩掉。这类缺陷在正常玩法下概率低、在极端策略下必现——
所以极端策略脚本顺带就是崩溃探测器。

检查方式：静态列出所有会改变存活状态的写入点，逐个确认它后面有结算调用。

## 七、观察性检查：干净上下文裁决怎么问

理解度裁决必须由**未接触任何策划 / 构建 / README 文档**的子代理出具，只喂按顺序截取的
真实画面与屏幕文本，回答逐字留档，主代理不得代答或转述。

这里有一条**决定裁决有效性**的追加要求：

> 必须明确要求裁决者区分「屏幕告诉我的」和「我本来就知道的」，并逐条标注来源。

改编知名原著时，裁决者认得人物和典故，会把设计从没上屏的信息当成已传达。加上这条要求，
它会自己说出「这几个名字对应的身份是我凭原著认出来的，画面上没有任何身份说明」——
这才是真发现。不加，它会流畅答完三问，缺口全部隐形。

同理适用于任何有文化知名度的素材：越有名，越要逼裁决者分清来源。

裁决的判据锚在**设计承诺**上：设计说「不熟原著也能上手」，那么「身份只能靠原著知识
补出来」就是这条承诺没兑现。设计没做这个承诺，同一现象就不算缺陷。

## 八、证据的三条硬要求

1. **落在工作区内的持久路径**，不在系统临时目录。临时目录路径按契约视为无证据，
   对应检查项不得记通过。这条会被反复违反——生成测试脚本时默认写 `/tmp` 太顺手了，
   所以要在构建说明里就把证据目录定下来。
2. **能复跑重建**。证据是结论的支撑，不是收藏品；命令写在报告里。
3. **按体积裁剪，但别按相似度裁剪**。

第三条有个陷阱：用感知哈希去去重证据帧会删掉不该删的。低分辨率灰度哈希看不出飘字、
HUD 数值和小范围演出的差异——三张记录不同阶段的关键帧会被判成完全相同。
**按「它记录哪一步」去重，不按像素去重**；真正的重复是同名同步骤连拍出来的那几张。

体积上，截图存 JPEG 而不是 PNG：同一批画面 PNG 七十多兆、JPEG 十兆左右，判读不受影响。
成人向内部验收帧放受限子目录并排除出版本库，可复跑重建。

## 九、时序证据只在常速下有效

加速 / 跳过参数下取得的一切时序证据无效，只能用于状态与结果断言。

测「首个有意义动作」时注意两件事：

- **回合制的「首个动作产生效果」包含下满一轮指令**。只给一个单位下指令不会结算，
  测不到状态变化。这不是脚本 bug，是这个类型的真实体验时长。
- **测量本身会占时间**（例如采样帧率的那两秒）。要么排除，要么在报告里说明该数字偏保守。

同时报出首屏加载、包体、帧率。若产品框架把性能预算记为 `N/A`（未锁定），那就
**没有可判超标的基准**——如实报数字，不据此判 `major`，把「未锁定预算」本身作为
`product` 归属的缺口留档。既不放过，也不虚构一个标准来判。

## 十、报告要把「没验的」写得和「验过的」一样清楚

未测试范围是报告最有价值的部分之一。逐条写：没验什么、为什么没验、要验需要什么。

有些东西是**结构上验不了**的，要说出结构原因而不是含糊过去。例如某个道具的反噬强度
足以让脚本化演示把该场翻成必败——那就说清「它留在通关路径外，规则层由固定种子断言覆盖，
视觉证据缺失」，而不是既不演示也不解释。

## 十一、自查清单

- [ ] 每个门槛都有下方/上/上方三点用例
- [ ] 期望值来自设计文档，写检查时没看实现常量
- [ ] 断言盯输入/输出，不盯内部函数名
- [ ] 每个演示分支都挂了断言
- [ ] 每条修掉的 blocker/major 都有失败过的回归
- [ ] 所有改变存活状态的写入点后面都有结算判定
- [ ] 理解度裁决要求了「区分屏幕告知与既有知识」
- [ ] 前提四问跑过，比对目标在跑门前已写死，且第四问与**选定方向**的同玩法先例字面比对
- [ ] 前提传达门 build 在灰盒期跑过一次并留了记录，QA 已在成品画面复跑
- [ ] 三段弧每期的结束标记与新增动词各有一组对照证据，同玩法动词清单逐条演示过
- [ ] 证据在工作区内、可复跑、按步骤去重
- [ ] 时序证据取自常速
- [ ] 未测试范围逐条写了原因
