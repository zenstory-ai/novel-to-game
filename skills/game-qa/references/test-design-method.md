# 测试设计方法

目标是用最少证据区分“能跑”“能交付”“能公开声明”，而不是把每个项目变成测试工程展示。

## 一、先从 profile 反推

1. 写出当前 profile 的 required set。
2. 加入玩家实际可用模式的效果检查。
3. 每个检查只保留能改变游戏效果结论的最小用例。

不要为 finish/profile 组合复制矩阵；同一断言在不同文件重复出现时，机器事实留在 verification，人读
解释由报告生成。

## 二、三类检查不要混

- **确定性检查**：状态迁移、门槛、结局、资源、重开。可自动断言。
- **观察性检查**：真实画面、输入链、可读性、上手、视觉目标。需要截图、录制或人工裁决。
- **主观试玩**：趣味、节奏、情绪、策略空间。只能记录样本观察。

机器通过不能替代观察性证据；人工喜欢也不能抵消确定性 FAIL。

## 三、从设计承诺写断言

先抄 GAME_DESIGN 中会改变结果的门槛、结局、冷却/破裂条件、三段弧结束标记和核心动词，再为每项
选择一个正例和一个最有区分力的边界/反例。断言盯住玩家可观察结果，不绑定内部函数名。

叙事主导项目照抄的对象换成：关键选择节点、持久旗标及其读取点、分支汇流点、结局条件、知识表
里"谁在第几场知道什么"，以及每处声明的延迟回响。最有区分力的反例通常是**反向路径**——没做
那件事的玩家走同一段，断言未选事实没有出现。结局区分用两条只在关键选择上不同的路径对跑，
断言最终玩家可见文本不相同。

确定性系统至少复现一次相同状态与输入得到相同结果。修复缺陷时补一条能重现原故障的回归，避免
只验证修后的 happy path。

## 四、一条完整路径胜过截图堆

从 clean start 走到设计结果再 restart。每个 checkpoint 只保留：触发输入、预期变化、状态证据、
运行环境证据、必要代表帧。只有语义发生变化时留新 checkpoint；不要为每次点击保存一张图。

时序、动效、碰撞和连续镜头证据必须在正常速度下采集；慢放只用于定位，不能证明体验正常。

## 五、干净上下文只在需要时用

`delivery` 及以上才默认验证首次上手。给未读策划的人或干净上下文顺序展示第一分钟真实画面，让其
回答：我是谁、要什么、什么会结束这一局、主要反复做什么。保存原话；不能回答是发现，不要用团队
解释替它补答案。

release 独立试玩只给玩家当前真实游戏和必要操作入口，不给实现辩解；记录能否独立完成核心路径及
玩家实际遇到的问题。graybox/smoke 不为获得“专业感”而强制拉 reviewer。

## 六、证据两条硬要求

- **持久**：工作区相对路径，文件真实存在；不引用 `/tmp`、缓存或个人桌面。
- **互补**：状态、runtime 和 visual 各证明自己的层，不互相冒充。

大型录屏、逐点击截图、raw trace 和可重建 contact sheet 不长期进 Git；保留生成脚本、摘要和当前
声明真正引用的最小代表证据。

## 七、报告诚实性

每个 NOT_RUN 写原因和阻断哪些 profile。当前 profile 的必需项被 limitation 阻断时整体 FAIL。
报告把“没验的”写得与“验过的”一样清楚，但状态词表不增加 `PASS_WITH_GAPS`。

问题按 product/design/art/build 归属。趣味、平衡、留存、商业价值放进人工试玩观察，不放进机器
PASS 数量。
