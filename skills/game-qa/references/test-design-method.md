# 测试设计方法

测试设计的目标是用最精简的实机证据验证游戏能否走通可玩闭环，不要把游戏项目做成繁琐的测试工程秀。

## 一、从六项结果反推

围绕 `launch`、`render`、`input`、`coreLoop`、`outcome`、`restart` 六项门禁，各挑一条最直观的实机观察证据。

## 二、从设计承诺写断言

对照 `GAME_DESIGN.md` 中会改变局势走向的数值门槛、结局条件、失败触发点、通关标记和核心动作，为每条核心规则各写一个正向通关用例和一个能暴露边界漏洞的反例。测试断言直接检查玩家可见的画面与状态结果，不死绑内部私有函数名。

叙事主导项目重点核查：关键分支选择、跨场持久状态读取、分支汇流后的一致性、结局解锁条件以及人物知情边界；系统主导项目重点核查：状态流转、属性门槛、资源增减、战败惩罚与重开清零。修复 Bug 时必须补一条能稳定复现原故障的回归断言，不能只测一路顺风的成功路径。

当项目维护了事件日志时，保存规则版本号、初始状态摘要、随机种子 `seed`、输入序列和终态摘要并完整重放一遍；随机猴子测试（Fuzzing）只用于探查死胡同和报错种子，不能代替真实的通关主路径。若接入了实时生成式叙事，必须额外构造四类反例断言：篡改既有原著事实、违背人物在场承诺、私自改写玩家已提交的行动、向不在场角色泄露秘密——生成模型的输出只算候选文本，测试断言一律以规则引擎最终提交的状态与玩家侧可见反馈为准。

当项目启用了身份专属命令（`signature_command`）时：正向用例从固定的规范化候选意图出发，验证相同初始状态、`seed` 与规则版本必然产出完全一致的执行轨迹与结算结果；意图解析层则用同义句、否定句、附加条件、缺失必填槽位和自相矛盾的指令做边界测试，允许系统追问澄清或拒绝执行，严禁静默误判成相反动作。反例需覆盖执行人不在场、资源不足、空间越权、人物不知情和违背既有承诺五种情形，确认规则引擎均拒绝提交状态；当指令仅部分执行或走漏风声时，界面反馈必须与实际留下的物证、目击者和知情变化完全吻合。对延期发作事项，需验证其不会提前触发、到期时确实重新推回玩家决策界面、只结算一次，且读档或重开后不会异常复活；自由交谈产出的事实、承诺、权限、拒绝和目击提案，同样必须先通过规则引擎校验。

局部热修（Patch）后，先重跑原故障复现路径，再跑一条共用上游状态但拐向相邻分支的反例路径。单纯替换文案或美术素材可保持状态摘要不变；一旦修改了变量含义、节点 ID、动作结算效果或知情权限，则必须验证旧存档与事件日志能正确迁移，或显式拦截并提示旧档不兼容。

## 三、一条完整路径胜过截图堆

从纯净启动（`clean start`）一路打通至设计结局，再触发重开（`restart`）。每个关键检查点（checkpoint）只记录触发输入、预期变化、状态快照、运行环境信息和必要的代表性画面帧；只有当游戏状态或画面语义发生实质变化时才新增检查点，不要每点一下鼠标就存一张截图。

涉及倒计时、动效过渡、物理碰撞和连续镜头调度的证据，必须在正常 1× 倍速下实机采集；慢放或单步调试仅用于排查问题，不能拿来充当正常游玩体验的证据。战斗反馈需对照真实战斗事件的出手方、受击方、实际伤害数值和属性克制关系，分别核验普通命中、属性克制与被克制三种表现，并确认在开启静音、开启减弱动态和跳过演出时依然能看清结算结果。对话框还需额外验证：长文本上下滚动、选中文本或弹出顶层遮罩时不会误触跳段，且点击继续按钮与按键盘快捷键均能正常推进。

代码源码、通关攻略与内存隐藏状态可用于验证底层规则逻辑，但不能证明初次上手的玩家单凭画面提示就能看懂规则或自己解开谜题。每当需要评估新手引导、界面提示或谜题线索是否清晰可寻时，必须另起一个从未读过源码、设计文档和攻略的独立试玩会话，只给它看正常游戏画面并只允许常规操作（严禁偷看源码、内部状态快照或答案配置）；若当前会话已经读过内部实现，其测试结果只能算“知情规则验证”，绝不能冒充真实新玩家视角的初见试玩。初见试玩需如实记录玩家看到的画面提示、实际尝试的操作与卡关位置。

文字或叙事主导项目需在目标视口尺寸下核查当前可执行操作、决策依据与结果反馈是否清晰可点，对照既定阅读动线排查文字遮挡、截断或按钮点不到的问题；多分辨率与极端长文溢出按实际风险抽检，不搞机械的全排列截图矩阵。

互动影游还需专项核验：剧本静态穷举需把限时抉择的超时沉默分支、察言观色热区的每种点击组合、身体动作的成功与失手全部作为独立分支一路验算到结局；限时倒计时在打开菜单、隐藏界面和切入后台标签页时确实暂停，倒计时归零确实落入沉默分支，且涉及个人意愿的选择绝无倒计时；画面热区在动态视频与回落静帧下均准确框住目标器物；做出选择后确实播放该选项专属的过场短片，字幕按分镜时间点自动换句、点击可提前跳句、打开菜单时视频暂停，且读档或关闭动态影像时能稳稳显示末帧定格图且不漏任何一句台词；凡是配过场的选择点，底下每个选项的过场视频文件均真实存在；网页端音频在玩家首次点击交互前绝不自动出声。注意浏览器后台标签页会节流 `requestAnimationFrame`，涉及计时与动作判定的测试必须在激活的前台窗口运行（若使用虚拟时钟替身须在证据中如实注明）。

图形界面需在实际显示尺寸下确认图标已正常加载且轮廓清晰可辨，必要的项目名称与操作说明均可顺畅查看；同时排查有无硕大的纯文字占位块、重复啰嗦的标签或常驻长篇规则说明挤占核心画面。图片文件 HTTP 200 加载成功只代表资源未缺失，不代表美术品质达标；发现的画面瑕疵按影响程度归入现有六项检查或记入已声明的完成度限制。包含多个功能面板的游戏需逐一打开各面板的代表性状态，检查统一的弹窗外壳、内容区滚动以及列表最末一项操作按钮是否可点；存在二级嵌套弹层时确认操作焦点留在最顶层。对于可取消的弹窗操作，点击遮罩空白处、按 `Esc` 键、点右上角关闭与点取消按钮必须产生完全一致的无副作用回退结果，并在关闭后恢复底层界面的正常操作；而必选分支与待结算步骤则需反向验证绝不会被点击背景空白处意外跳过。手机窄屏视口下还需确认核心导航入口依然可见可点，防止 CSS 媒体查询一刀切隐藏了关键功能。

包含角色连续行走的项目，必须从角色的真实当前坐标出发实测整段移动路线，不能只做网格中心点或寻路节点的静态连通性检查；实走路线需覆盖拐角绕行、死路折返、边界阻挡和隔着障碍物交互。扩充或重绘地图后，需实测从场景入口走到任务点、传送出口和支线的真实移动轨迹、右上角小地图坐标换算，以及旧存档遗留坐标下的实体依然可正常接近交互。实走验证需记录抵达终点时的距离误差与连续脚底坐标序列，防止角色才走两步就卡住停下却被脚本误判为寻路成功；同时直接对照画面上的建筑墙根、桥面边缘与水岸线核查穿模，不能只让寻路算法自己验证自己的碰撞数据。静态网格连通性测试与单张画面截图各自只证明规则层和渲染层的一角，两者都不能单独证明角色在实机里真的走到了目标点。

## 四、证据要求

所有证据路径一律使用项目工作区内的相对路径且文件必须真实存在，严禁引用系统临时目录、浏览器缓存或个人桌面路径；检查状态取值与 `limitations` 格式严格遵循 [qa-contract.md](qa-contract.md)。

体积庞大的全程录屏、每次点击的连拍截图、原始调试日志以及可随时由脚本重新生成的抽帧九宫格预览图不要长期提交进 Git 仓库；仓库内只保留当前 `qa/verification.json` 明确引用的最小代表性证据。验证发现的一切问题按 product / design / art / build 职责归属退回对应环节处理。
