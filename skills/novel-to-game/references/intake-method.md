# 需求 intake：先框定产品，再动手

小说转游戏最贵的错误都发生在写一行代码之前——**平台选错、类型选错、画风选错、
尺度选错、核心幻想没定**。这些决定一旦被下游各阶段各自默认，做到一半才暴露，返工代价
极大。需求 intake 这一步的职责，是把这套**产品框架**变成一次显式、用户确认、之后不可静默改写的
事实（`PRODUCT_BRIEF.md`），供拆解、概念、设计、美术、构建全程遵守。

**用户第一次给出小说时，必须先做这一步，再进拆解。**

## 怎么问：先给默认值，不要连环追问

不要甩一串空问题给用户。正确姿势是**先读懂原作、替用户填好一份推荐草案，再请他确认或
改**：

1. 速读原作足够判断：语言、题材、基调、时代/设定、有无成人/暴力/情爱内容、情绪内核。
2. 由此为每个维度**推出一个有依据的推荐默认值**（语言→市场→对标；题材→类型+画风；
   基调→分级）。参考 [intake-benchmark-reference.md](intake-benchmark-reference.md)——它是
   **凭通用知识整理的起点参考，不是已核实的结论**。真要拿去给用户当默认的那几款对标，
   **先用 WebSearch 联网核实**其机制、平台与现况（尤其较新或小众的作品）；联网不可用时，
   把对标标注为「凭记忆·未核实」再呈现，不当作确定结论。
3. 把整份草案摆给用户，请他确认或逐项改。离散的高杠杆选择（平台、画风、分级/NSFW、
   类型/对标方向）用 AskUserQuestion 提，推荐项放第一并标（推荐）；核心幻想一句话用自由
   文本。一次问清关键几项，别追问到底。
4. 仅当下列任一成立时才按默认值推进：用户显式要求全自动（如说 autopilot、别问我）、
   AskUserQuestion 等提问工具不可用、或提问后用户未响应。此时在 `PRODUCT_BRIEF.md` 里把
   每条标为**未确认假设**并醒目列出，让后续任何人一眼能挑战。`quick` 模式不属于此列，
   照常先问。

## 必定维度（intake 清单）

维度清单以 [pipeline-contract.md](pipeline-contract.md) 交接门表为唯一权威，本表给每一维的
操作方法；未定的维度记 `N/A`，`N/A` 也是锁定值，下游不得自行补默认。

| # | 维度 | 要定什么 | 默认从哪来 | 不定的代价 |
|---|---|---|---|---|
| 1 | 平台与形态（含性能预算） | 客户端(PC/主机) / 网页 / 小程序 / 移动App；窗口/全屏、竖屏/横屏、主设备与输入方式；**目标分辨率与最低分辨率**（如桌面横屏 1280×800 起；移动竖屏 390×844 起）；**按目标平台锁启动时间 / 总包体上限 + 目标帧率** | 体量与题材：重叙事重养成→客户端/App；即开即玩/社交传播→网页/小程序；包体/启动事实见引擎参考 | 决定 UI、控制、时长、体量、画风上限；性能预算不锁会在做完后才暴露超包体；显示与输入不锁会让构建与 QA 各自发明验收门 |
| 2 | 目标市场与界面语言 | 主市场、首发界面语言 | **小说语言→对应市场**（硬规则，见下）；界面语言默认=市场语言 | 决定对标、类型惯例、内容敏感点、文化符号 |
| 3 | 游戏类型 + 对标名作 | 主类型/子类型 + 2-4 款该市场玩家真正熟知的对标，逐款标「借用层级」：**同玩法**（本作核心动词与循环结构就是它那一套）/ **仅原则**；**同玩法至少 2 款**，并写出共有的 3-5 个核心动词与一句循环结构 | 题材→类型常见映射 + 参考表 | 单一最强锚点；不定则概念阶段全靠猜。只锁子类型不锁同玩法先例，下游会把窄子类型自创成没人认得的循环 |
| 4 | 美术画风 | 像素 / 2D手绘 / 立绘+背景 / 2.5D / 卡通渲染3D / 写实3D / 水墨工笔… | 由平台 × 题材 × 体量推 | 决定辨识度、制作可行性、招牌画面 |
| 5 | 内容分级 / NSFW | 全年龄 / 12+ / 16+ / 成人向(暗示) / 成人向(露骨 NSFW)；若露骨，定**热度天花板** | 由原作尺度 + 市场 + 平台合规推 | 定错则文案与美术全线返工 |
| 6 | 核心幻想 / 情绪卖点 | 一句话：玩家扮谁、要什么、该在哪"爽/怕/心动" | 由原作情绪内核推 | 不定则做出"系统正确却没人想玩"的东西 |
| 7 | 单局时长与结构 | 垂直切片时长；单局 vs 长线；有无养成/日常循环 | 默认 10-30 分钟可完整游玩切片 | 决定循环密度与范围 |
| 8 | 发行/商业化定位（未定记 N/A，但常影响玩法） | 买断/独立发行 vs 免费+内购/抽卡/体力 | 由平台 + 市场推 | 决定是否需要 gacha、日常、资源循环 |
| 9 | 游戏引擎与交付运行时 | **生产引擎**（Unity / Unreal / Godot / Cocos / Ren'Py / Phaser / Three.js…）+ **目标交付运行时**（PC 可执行文件、主机/移动设备、引擎运行器、小程序开发工具、浏览器等）+ 当前环境无法运行目标时才填写的**替代验证运行时** | 由平台×画风×题材×市场×当前可用工具链推；见引擎参考表 | 定错会造成平台/画风错配；不区分目标与替代运行时，会把方便测试的版本误报为目标平台已交付 |
| 10 | 玩家结构与社交形态 | 单人 / 本地多人 / 异步社交 / 实时联机；成品是否需账号 / 云存档 / 榜单 / 好友 / 公会 / PVP | 从小说 + 对标推：宅斗攀比→异步社交榜；SLG→同盟；乙女→伪即时通讯 | 反向决定核心玩法与留存结构；漏了会"开局就没在做那个游戏" |
| 11 | 受众画像 | 硬核度（硬核策略 / 中度 / 轻度休闲 / 挂机党）；性别向（男性向 / 女性向 / 乙女 / 全性向）；玩家动机原型（挑战成就 / 竞争攀比 / 社交 / 沉浸叙事 / 收集养成） | 由题材 + 市场 + 对标推 | 决策密度 / UI 密度 / 单局时长 / 教学强度的标尺；不定则下游"深度够不够、上手快不快"全靠拍脑袋 |

**补充纪律**：
- **核心幻想（#6）**：一句话必须点名玩家在哪个具体时刻产生什么情绪；只有玩法动词/系统
  名词即不合格——机制归类型维度（#3）。正例：「夜里决定去谁屋里——今夜快活，明早要接住
  另外两人的醋、债和条件」；反例：「指挥回合战斗、五行克制、变化潜入，一路打通名场面」
  （全是机制，无情绪落点）。
- **玩家结构（#10）**：交付切片按这里锁定的结构实现。社交或联机若属于核心幻想，至少要在
  目标运行时提供能真实改变结果的最小多人或异步路径；AI 假多人或占位榜只能作为明确批准的
  替代验证，不能证明联网体验已交付。若首版确定为纯单人，也要写清长期结构是否预留账号、
  云存档或异步数据边界。
- **游戏类型（#3）**：玩法取自已被大量玩家玩过的**成熟打法**，小说只做 IP 皮——世界、人物、
  剧情、题材与美术归小说，核心动词与循环结构归先例，**发明新机制恒为非目标**。凑不满 2 款
  同玩法先例就换一个有先例的打法，文学契合度不构成豁免。类型下面再锁一格**空间形态**：
  2D 界面（玩家不操纵空间）/ 2D 空间（走位、地形）/ 3D 空间（走位 + 视角）。具体选择跟随
  类型与同玩法先例；取「2D 界面」必须由用户显式确认，并写明这个玩法为什么不需要玩家操纵
  空间与视角。小说是文字的，游戏不必跟着变成文字——把书的形态当成玩法的形态，正是这一格
  要挡下的事。
- **教学强度不是可以归零的维度**：把上手方式锁成“无教程 / 全靠演出 / 纯 diegetic”是**风格
  选择，不是沟通豁免**。无论哪种风格，玩家都必须在**第一分钟内**知道三件事——我是什么、
  我要什么、什么会终结这一局；锁风格时必须同时写明这三件事用什么手段送达。只写“不做教程”
  而不写送达手段，视为该维度未锁定。
- **受众画像（#11）**：先定画像，再拿对标验证成熟打法——**对标是画像的证据 / 落地，不是替代**。
- **性能预算**：把引擎参考里已核实的包体 / 首屏事实（如微信主包 ≤4MB、抖音整包 ≤20MB）从
  "参考背景"升为**锁定产品事实**，挂在平台维度下（首屏加载 / 总包体上限 + 目标帧率），进上游
  保护范围，构建完成证据强制核对。

## 三条硬规则

**语言→市场→对标**：小说是什么语言，就对标那个市场里玩家真正熟悉的名作——中文小说
对标中国市场爆款，英文对标西方，日文对标日本，韩文对标韩国。对标分两层，别混用：核心
玩法循环必须与**至少 2 款**对标**同玩法**（核心动词与循环结构就是它们那一套，说得出
共有的 3-5 个动词与一句循环结构才算），画风、商业模式、UI 惯例这类才可以**只借一条
原则**。每款标注借用层级与借的是什么，不是拿名字装饰，也不能拿另一市场的成功直接证明
本地接受度。**玩法取自成熟先例，小说只做 IP 皮——发明新机制恒为非目标。**映射与候选见
[intake-benchmark-reference.md](intake-benchmark-reference.md)。

**尺度与平台互相约束**：分级不替用户默认最保守，也不替用户放开——**必须显式确认**。若
用户要 NSFW/露骨，要当场点破它对平台与发行的约束：小程序与多数应用商店禁成人内容，
露骨内容通常只能走网页/PC/特定成人平台。分级定了要连**露骨档的热度天花板**一起定
（暗示 / 点到肌肤即止 / 解衣肌肤气息但视角克制 / 更直白），避免"放开了"却没说放到哪。
无论分级多高，**不涉及真实人物、不性化任何未成年角色**是不可逾越的底线，与用户偏好无关。

**引擎跟着平台×画风×题材走，且要联网核实**：游戏引擎属于产品决定，要随平台、画风、题材、
市场一起确定。**先用 WebSearch 核实候选引擎的当前版本、目标平台导出能力、许可与商业条款**
（引擎生态逐年变，尤其主机/移动/小程序渠道与开源引擎），联网不可用则标"凭记忆·未核实"。
同时写清**生产引擎、目标交付运行时、实际验收设备或运行器**。当前环境缺少目标工具链时，
可另列用户批准的替代验证运行时；不能自动改成网页，也不能用替代运行结果证明目标平台已经
通过。映射与候选见
[intake-engine-reference.md](intake-engine-reference.md)。

## 产出：PRODUCT_BRIEF.md

一页锁定这十一个维度，外加：对标矩阵（每款带「借用层级」列——同玩法项写出共有的核心动词与
循环结构，仅原则项写借哪一条）、明确非目标（**发明新机制恒在其中**）、合规注意、以及所有
**未确认假设**清单。它进入"上游事实不得下游静默改写"的保护范围（见
[pipeline-contract.md](pipeline-contract.md)）：概念继承、美术读画风与平台，构建读取目标平台、
生产引擎、目标交付运行时和可选替代验证运行时；任何阶段要改产品框架都回这里显式改。
