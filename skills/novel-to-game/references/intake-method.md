# 需求 intake：先给推荐，再处理高风险歧义

intake 的目的不是举行十一项审批会，而是尽早锁住会让下游返工的产品边界。先读来源，替用户写
一页推荐草案；低风险空白列为未确认假设并继续，只有 materially branching 或安全相关决定才停靠。

## 默认动作

1. 速读到足以判断语言、题材、情绪内核、时代设定和内容尺度。
2. 依据原作与用户用途给出一个完整推荐，而不是连续抛空问题。
3. `quick` 默认 `assuranceProfile: smoke`；交给他人试玩或指定设备验收时推荐 `delivery`；需要面向
   最终用户验证目标设备性能、必要资产降级和独立试玩时推荐 `release`。
4. 只在以下情况停下来问：
   - 平台、核心玩法或核心幻想存在两个会生成不同产品的方向；
   - 成人内容、真实人物、未成年人、版权或资产授权边界不清；
   - 目标运行时、付费服务或不可逆制作投入需要用户承担；
   - 权利、秘密或公开范围会带来产品安全风险；这些问题在 intake 处理，不包装成 QA 检查。
5. 其余未定项写进 `PRODUCT_BRIEF.md` 的「未确认假设」，标注推荐依据和影响；下游若要改变，回到
   brief 显式修订。

联网只用于会影响真实决定且可能变化的事实，例如当前引擎导出能力、许可证、渠道限制和新服务
规格。不要为了给每个常识默认值找出处而把 intake 变成研究项目。

## 产品框架

填这张表前先读两份参考，它们提供的是**推荐默认值**，不是结论：
[intake-benchmark-reference.md](intake-benchmark-reference.md)（市场 × 题材 → 对标 / 平台 / 画风；
**原著价值在人物、关系、悬念或道德困境时直接看第 1.5 节的互动叙事路线**）与
[intake-engine-reference.md](intake-engine-reference.md)（引擎与运行时选择）。不读就填「类型与先例」
和「引擎与运行时」，等于凭记忆写下游要照着做的锁定值。

以下十二维用于形成草案，不要求用户逐格确认：

| 维度 | 最小锁定内容 |
|---|---|
| 平台与形态 | 交付物、目标/最低显示模式、输入方式、性能预算 |
| 市场与语言 | 目标市场、首发界面语言 |
| 类型与先例 | 主玩法、2 款同玩法先例、3–5 个核心动词、空间形态 |
| 主要承载 | `experienceProfile`：`system-led` / `narrative-led` / `hybrid`，即体验主要由动作规则、连续场景与对白，还是两者分层承担 |
| 美术与完成度 | 画风、`targetFinish`、参考维度/权利边界、投入边界 |
| 内容尺度 | 分级；成人内容的范围与平台约束 |
| 核心幻想 | 玩家扮谁、追求什么、在何时产生什么情绪 |
| 时长与结构 | 验证切片时长、单局/长线结构 |
| 发行定位 | 买断、免费、N/A；只记录会影响玩法的部分 |
| 引擎与运行时 | 生产引擎、目标交付运行时、可选替代运行时 |
| 玩家结构 | 单人/多人/异步/实时，以及切片内真实范围 |
| 受众 | 硬核度、主要动机、上手与信息密度 |

另列 `assuranceProfile`，它不是第十三个产品维度，而是验收强度。`targetFinish` 管成色，profile 管
证据深度；二者不得互相推断。

未适用的维度写 `N/A`。这意味着明确不做，而不是允许下游自行补默认。

## 三条安全规则

- **尺度与平台互相约束**：成人内容必须显式锁定上限和发行边界；不涉及真实人物，不性化任何
  未成年角色。
- **目标与替代运行时分开**：记录生产引擎、目标交付运行时和实际测试运行时；替代结果只证明其
  覆盖层，不得包装成目标平台已交付。
- **参考只借声明维度**：玩法先例用于循环，视觉参考用于构图/材质等指定维度；不得顺手搬入角色、
  UI、世界设定或未经授权资产。

## 输出：PRODUCT_BRIEF.md

一页写清：十二维推荐、`targetFinish`、`assuranceProfile`、明确非目标、合规/权利边界、未确认假设、
需要用户裁决的阻断项。只有阻断项为空才进入拆解；普通未确认假设不阻断 `quick`。
