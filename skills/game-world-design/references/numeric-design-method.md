# 数值与实现一致性

仅在资源消耗、属性门槛、结局条件或局势压力真正读取数值时使用本方法，不为设计文档堆砌无实际作用的装饰性数字。

## 可达性与取舍

每个关键数值都必须写明实际含义、增减来源、后续读取点和玩家可感知的界面反馈。对会卡住流程或改变结局走向的数值门槛，直接按代码实现将采用的公式演算典型路径，分清「设计预期的挑战失败」与「数值配错导致的意外死局」。

当项目承诺存在策略取舍时，先写明出现什么现象代表该策略承诺落空，再对比能暴露数值失衡的测试路径（涉及随机因素时固定 `seed`）。数值差距多大才算有体感由本项目自行定义，不生搬硬套通用的倍率、胜率或回合数标准。单线推进、不可再生资源或仅用于战果统计的记录型数字本身并非设计缺陷，均以本项目的体验承诺为准。

涉及人物承诺、证词真伪、器物归属等具体历史时，优先用布尔或枚举状态记录事件本身，不默认折算成笼统的好感或关系总分。

## 漂移裁决

当设计文档与代码实现的数值不一致时，必须逐项核对并做出裁决：要么采纳经实机验证合理的实现值并同步回写设计文档，要么修正文档笔误，要么要求代码按原设计承诺修复——未经逐项核实的批量覆盖不算有效裁决。

设计交接时需确认：关键路径按既定数值均可走通、反例路径能正常暴露设计风险、文档与代码之间无悬而未决的数值偏差。有限路径的数值演算只保证主干可达，不等于证明了全局无死局、长线经济平衡或主观体验好玩。
