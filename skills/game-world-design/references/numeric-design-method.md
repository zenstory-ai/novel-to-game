# 数值策划方法

数值不是「填一张表让手感差不多」，而是把已声明的取舍变成**可演算、可证否**的东西。
本文只讲方法，不给某个类型的具体数值——数值随类型和原著变，方法不变。

判断标准很简单：**任何一句「玩家要在 A 与 B 之间权衡」，都必须能演算出这个权衡存在。**
演算不出来，那句话就只是愿望。

## 一、先定量纲，再填数字

填任何数字之前，先答这四问。答不上来就不要填，填了也是假精度。

1. **这个资源衡量什么**：一句话，用玩家能感知的词，不用系统词。「身体耗损」比
   「strain 值」有用，因为前者能推出它该在什么时候变化。
2. **它的产出口有哪些，投入口有哪些**：逐个列。**只有产出没有投入的资源必然通胀**，
   只有投入没有产出的资源必然把玩家逼到死角。
3. **它的稀缺比**：一局之内，产出总量除以「玩家想花的总量」。这个比值就是难度旋钮，
   而不是敌人血量。比值 ≈1 是紧绷，>1.5 基本等于这个资源不存在。
4. **它被谁读取**：至少一个规则读取点——选项门槛、事件触发、结局条件、或可见的能力
   限制。写不出读取点的资源就不要做，更不要放上 HUD（见第四节）。

## 二、数值预算表：每档门槛都要演算可达

一张表，一行一个门槛，逐行回答「在切片预算内，玩家凭什么走到这里」。

| 列 | 内容 |
|---|---|
| 门槛 | 设计声明的那个数字或条件 |
| 预算内取值 | 玩家到这一步实际能拿到的量 |
| 演算 | 从起始值 + 各产出口累加，写出算式，不写「差不多够」 |

预算表的价值在于**它会否掉自己**。常见的三种否掉方式：

- **门槛不可达**：算下来最多攒到门槛的八成 → 要么降门槛，要么加产出口，
  **不要靠玩家运气好**。
- **门槛太易达**：起始值就过线 → 这个门槛没有在做决策，删掉或抬高。
- **门槛只有一条路可达**：唯一解不是取舍。要么补第二条路，要么承认它是剧情门而非选择。

预算表必须对着**成品引擎的实际常量**演算，不是对着设计稿里的期望值。这两者会漂移，
而且漂移是常态（见第六节）。

## 三、取舍要能被极端策略证否

设计声明的每一条取舍，都要配一条**会让它失效的极端策略**，然后真的跑。

方法：把引擎从界面剥离，写两到三个纯策略脚本，用固定种子跑完整局，比较最终状态与结局。

- **纯 A / 纯 B**：各只用取舍的一边。
- **混合**：交替使用，代表半熟练玩家。

读结果的三条判据：

- 某条单一策略通吃 → **取舍不存在**，玩家从没真正做过选择。
- 两条极端走到同一结果 → **选择没有后果**。
- 混合策略不落在两个极端之间 → 数值里有非单调的东西，通常是 bug 而非深度。

关键在于**极端策略要从设计声明的否决现象里推出来**，不是随便写两个打法。设计写
「无视相克也能以相近回合数通关就算失败」，那条极端策略就是「全程无视相克」，
判据就是回合数比值。声明什么，就跑什么。

比值要事先写进设计当作**可测张力目标**（例如「劣势策略应付出 1.4–2.5 倍代价」），
事后再看数字就变成给结果找理由了。

## 四、只写不读的量表是最常见的数值缺陷

一个资源被反复修改、常驻显示在 HUD、玩家盯了一整局——然后没有任何规则读它。
这是**每次都会出现**的缺陷，因为写入点是随手加的，读取点要专门设计。

自查方法：静态列出所有被写入的资源与旗标，逐个找读取点。找不到的，二选一：

- **给它一个读取点**，或者
- **从 HUD 上撤下来**，降级为纯记录。

给读取点时有个陷阱：最容易想到的读法是「到阈值就锁内容」，而这往往是用一个更糟的缺陷
换掉原缺陷——玩家被数值挡在剧情外面，比代价条不结账更伤。

**更好的读法是限制行动广度，而不是限制内容访问**：高耗损时那几个需要露面撑场的选项
不可选，但每条线的内容都还在。玩家付了代价，付的是「这一天做不了那么多事」，
不是「这条线你看不到了」。

同理适用于旗标：承载命运感的伦理选择只落一次性数值、后续没人回读，越是关键的选择
越严重。

## 五、把难度写成可测目标，不写成形容词

「中后期要有挑战」不可验收。可验收的写法是绑定基准策略的区间：

- 「用基准策略打，决战应耗 4–7 回合」
- 「劣势策略总时长应为最优策略的 1.4–2.5 倍」
- 「任一策略在任一种子下都应能通关」（无死局）
- 「诱饵指标在前两幕应能被追求它的打法可见地抬升」

每条目标配一个基准策略脚本和固定种子。**没有基准策略的目标不是目标**，因为不同人
心里的「基准玩法」差得很远。

## 六、数值一定会漂移，所以要机器盯

打磨期的调参发生在实现侧，回写文档永远排在最后，然后就没了。这不是纪律问题，
靠「记得回写」解决不了。

做法：写一份**独立不变量检查**，期望值逐条从设计文档反抄（每条标注它出自哪一节），
对照成品引擎的实际导出值，输出「一致 / 漂移」表。它必须：

- **不引用实现方自测的任何断言或常量**——用实现自己的常量验收实现，只能证明自洽。
- **能复跑**，一条命令出结果，进 CI 或至少进交接清单。
- **引用章节名而不是行号**，行号会随编辑腐坏。

发现漂移时，逐条裁决方向，不要整批处理：

| 情形 | 裁决 |
|---|---|
| 打磨期的平衡决策，经过试玩 | **采纳实现值**，回写文档 |
| 文档写错了，实现才是对的 | **改文档**，并写清为什么原写法不成立 |
| 实现悄悄多做了机制 | **补记入文档**，它现在是设计的一部分 |
| 实现少做了文档承诺的东西 | **回实现补**，这是缺陷不是漂移 |

第二种最容易被忽略，也最值得留痕：判断「文档错了」需要说出错在哪——比如某个法宝
被写成只对某一属性的敌人生效，而它存在的意义恰恰是那场对手不是该属性的决战，
那么「只对该属性生效」这个写法会让它在最需要它的一战完全失效。这类修正要写进文档，
否则下一个人会照着错的那版又改回去。

## 七、交接前的自查

- [ ] 每个资源都有量纲、产出口、投入口、稀缺比、至少一个读取点
- [ ] 数值预算表逐行演算过，没有「差不多够」
- [ ] 每条取舍配了极端策略，跑过固定种子，比值落在事先声明的区间内
- [ ] 无只写不读的资源与旗标
- [ ] 难度写成绑定基准策略的可测区间，不是形容词
- [ ] 独立不变量检查存在、可复跑、且当前零漂移
