# 游戏世界设计方法

## 可被推翻的体验假设

把核心体验目标落到具体的玩家动作、看得见的局面变化和失败表现上。可玩范围服从 `PRODUCT_BRIEF.md`，白盒保真度只需覆盖最大设计风险：纯文字推演可以验证叙事分支因果，但不能证明实时操作手感、空间走位、物理碰撞或镜头调度成立。

每个系统都必须实质影响玩家的核心决策；删掉或改为自动托管后玩家体验毫无变化的系统，一律砍掉。不要拿固定游玩时长、系统数量、角色等级跨度或固定的“五步关卡模板”代替针对本项目的范围判断。

## 品类外壳与第一分钟

仅适用于 `system-led` 或 `hybrid` 项目（`narrative-led` 跳过本节）。采用成熟品类时，玩家默认该品类必备、一旦缺失就会显得像半成品 Demo 的基础外壳（进入世界与移动、目标指引、成长反馈与重返动力，例如回合制 RPG 的城镇行走与 NPC 交谈、任务追踪、明雷遇敌、可重复的日常支线），必须在设计文档里用短表逐项标明「实现 / 降级 / 不做及理由」。首个可玩版本可以压缩地图和剧情体量，但不能砍掉品类外壳，也不得拿「不改变核心决策」为由裁剪外壳；无需为外壳另写复杂规则，只需把通关路径上会经过的外壳操作写进最小可运行规则。

玩家进入游戏的第一分钟内，必须看到该品类的招牌画面，并借该品类熟悉的界面指引一眼明白自己是谁、眼下要去哪里、下一步点什么。

扩充可探索场景时，先规划主干道、支路、视觉地标与绕路收益，再敲定地图画幅。新增空间必须带来路线抉择、世界认知加深或有后果的互动；用实际跑图时的事件密度和重访变化衡量场景是否充实，不靠拉大画布面积、堆砌无交互装饰或重复跑腿领奖凑数。

## 可执行因果

只写运行时真正消费的规则：

`当前状态 + 玩家行动 + 世界规则 → 新状态 + 可读反馈 + 后续机会`

每个关键动作写明前置条件、执行效果、不可突破的硬约束和后续读取点；需要跨场引用或回放验证时分配稳定标识。仅针对秘密、证词、伪装欺瞒等存在信息差的高风险事实，才区分「客观世界真相、玩家当前已知、剧中人物已知或误信」三层状态；普通公开事实不维护多层知情账本。

用代表性游玩路径检验核心承诺：玩家的操作如何改变事件原因或走向，世界又在后续哪个节点回读该操作。同时按项目定位区分「原著因果重演」与「策略博弈取舍」：玩家能照着原著步骤走通结局，不代表游戏里存在有意义的策略权衡。只有当项目明确承诺策略取舍时，才需列出不同选择之间的代价、收益及能暴露“无脑最优解”或“假选项”的检验局面；若项目本就是单解谜题或线性剧情重演，直接按线性重演设计，不必为了凑策略深度强加多解、养成或额外系统。只有承诺多周目重玩价值的项目，才要求设计可复现的随机变数。

## 身份专属命令与延期回响

仅在 `CONCEPT.md` 启用了 `signature_command` 时使用本节：

`玩家表述 → 解析候选 → 澄清或拒绝 → 规则验证 → 执行阻力 → 提交实际结果 → 证物/知情变化 → 到期回响`

`GAME_DESIGN.md` 需固定 `id / label / intents / slots / validators / commit` 六组最小结构；具体候选字段按项目实际需要增减，不强求数量一致或字段大一统。遇到否定句、附加条件、自相矛盾或超出支持范围的指令时，系统必须向玩家追问澄清或明确拒绝，绝不能仅凭关键词命中就自作主张把玩家的意思反着执行。

确定性规则器掌握唯一的状态提交权，负责逐一校验资源是否足够、执行人是否配合、空间权限是否放行、人物是否知情、是否与既有承诺冲突以及是否越过原著硬边界。界面反馈必须分清「玩家下达的安排」与「实际落地的执行结果」，清楚展示留下的物证、目击者和待发作的后续事项，不能靠生成一段含糊的文学描写掩盖结算结果。

延期发作的事项需记录来源动作、触发到期条件、关联人物/器物/承诺、当前状态及结清事件；一旦到期必须重新推回玩家面前做决策，不能只弹一行无关痛痒的装饰文本。即便允许玩家与角色自由私聊，私聊也只能产出事实、权限或承诺的候选提案，必须通过同一套规则校验后才能改写世界状态；原始聊天记录和模型打分不能直接写入权威游戏状态。

## 进程与世界反馈

顺着本项目的完整通关路径组织局势演进和结局触发条件，不强套“探索—成长—成熟”三段论。凡是作为核心卖点的原著规则，必须在运行过程中真正影响玩家的可选机会、行动代价或 NPC 行为，不能只写在背景设定或技能说明里。如果删掉某条规则后游玩结果几乎没变，要么直接删掉它，要么补足它在局势中的真实份量，不要靠再塞一个新系统去掩盖原规则的空转。

当叙事承担核心体验时，人物知情、声口与分支汇流规则见 [narrative-design-method.md](narrative-design-method.md)。

## 白盒反馈与局部修订

保留足以复现问题的初始状态、输入序列与预期终态；涉及随机因素时固定 `seed`，涉及事件回放时记录内容与规则版本号及事件序列。白盒试玩暴露问题后，按「出错位置、预期与实际差异、归属规则、负责环节、最小改动方案、复测路径」精准定位并做局部修订，不要动辄推翻重写整份设计稿。

一旦修改了状态变量含义、动作结算效果、人物知情权限或不可逆承诺，需同步迁移受影响的旧存档与事件日志，或明确声明旧档失效。修订后先重跑原失败路径，再跑一条能排查相邻分支被误伤的反例路径。验证通过只代表已覆盖的具体规则与路径成立，不等于证明了主观好玩或长线数值平衡。
